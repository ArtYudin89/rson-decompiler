# Технические детали

Справка по формату `.scr`, устройству парсера, round-trip-пересборке и раскладке
полотна. Пользовательская инструкция — в [../README.md](../README.md).

## Состав репозитория

```
decompiler.py       ядро: парсер .scr -> структура -> .rson
run.py              CLI-раннер: батч, --check (round-trip), Lang.dat->Lang.txt,
                    подкоманды `blockpar` и `pkg`
srpkg.py            .pkg архивы: list/unpack/pack/verify (RAW и ZL02/zlib)
srgi.py             изображения gi/gai/hai -> PNG: info/decode/verify (stdlib+zlib)
_dlgwatch.py        авто-закрытие модальных окон RScript.exe (Windows)
validate.py         сверка G/S/D-счётчиков с эталонными .rson
rsons/              эталонные .rson (ground truth для валидации)
Modding_Manual/     справка сообщества по формату/функциям скриптов
```

## Пайплайн

1. `decompiler.parse(data, lang)` разбирает бинарник в структуру
   (`Visual.Objects` + `Visual.Links`) и раскладывает объекты по полотну.
2. `decompiler.decompile()` пишет RSON (JSON с фиксированной шапкой
   `FileID`/`FileVersion`/`ScriptName`).
3. `run.py` для каждого `.scr`: находит `Lang.txt`/`Lang.dat` (вверх по дереву,
   `CFG/Rus/` и корень), при необходимости конвертирует `Lang.dat`
   BlockParEditor'ом, декомпилирует и опционально делает контрольную пересборку
   (`--check`).
4. При `--check`: RSON компилируется `RScript.exe --cli`, результат
   выравнивается бинарным патчером (см. ниже) и сравнивается с оригиналом
   побайтово.

## Формат бинарника

Раскладка `.scr` полностью задана загрузчиком игры, искать в файле ничего не
нужно: `TScript.LoadFromBuffer` и, для заголовка, `CompileScriptTemplateCondition`
(`source/script/aScript.pas` декомпиляции движка SpaceRangersHD_decomp),
переменная — `TVarEC.LoadFromBuffer` (`EC_Expression.pas`), строка —
`TBufEC.ReadWideString` (`EC_Buf.pas`). В `decompiler.py` это
`read_scr_layout()`; `parse()` строит RSON поверх неё. Так прочитаны до
последнего байта все 2424 `.scr` корпусов на 12.10.2026 (моды Steam, кэш
агрегатора, корпус RScript 4.14f, 40 стоковых скриптов; версии 5–8).

### Типы полей

- `u8`, `i32`/`u32`, `f32`, `f64` — little-endian; файл не выровнен по 2 байта
  (поля `u8` сдвигают выравнивание), UTF-16 декодировать только от начала поля.
- `wstr` — UTF-16LE до нулевого слова, **без префикса длины** (во всех версиях
  и при любом числе глобальных переменных). Правки кода, меняющие длину строки,
  безопасны.
- переменная: `wstr` имя, `u8` тип, значение по типу: `1` Int и `2` Dword —
  `u32`; `3` Float — `f64`; `4` Str — `wstr`; `9` Array — вложенный список
  переменных (`i32` число + элементы, имена элементов обычно пустые); у
  остальных типов значения нет.
- список переменных: `i32` число + переменные.

### Порядок

| Поле | Состав |
|---|---|
| версия | `u32`, игра грузит 5–8; RScript 4.10f и 4.14f пишут 8, старые сборки — 7 |
| смещение тела | `u32` (загрузчик берёт младшее слово и переходит туда) |
| глобальные переменные | список переменных (их число = слово по смещению 8, `h2`) |
| глобальный код | `wstr` — условие запуска скрипта; тело начинается сразу за ним |
| локальные переменные | список; RScript объявляет переменную на каждый объект (звезду, планету, место, предмет, группу, диалог) со значением-индексом |
| созвездия | `u32` число |
| звёзды | `i32` число; звезда: `wstr` имя, `i32` созвездие (−1 — нет), [v<7: `u8`], `u8` NoKling, `u8` NoComeKling, `i32` число связей × (`i32` звезда, `u32` DistMin, `u32` DistMax, `u8` Hole) [v<7: связь 29 байт], `i32` число планет × (`wstr` имя, 4 × `u32` раса/владелец/экономика/правительство, 2 × `u32` RangeMin/Max, `wstr` диалог), `i32` число кораблей × (`u32` Count, Owner, Ship.Type, `u8` Player, 5 × `u32` скорости/оружие/захват/место, [v<7: 2 × `i32`], 6 × `u32` статусы, [v<7: 2 × `i32`], 2 × `f32` StrengthMin/Max, `wstr` Ruins) |
| места | `i32` число; `wstr` имя, `wstr` звезда, `i32` тип и по типу: 0 — `f32` Angle, `f32` Dist, `u32` Radius; 1, 4 — `wstr` объект, `u32` Radius; 2 — `wstr` объект; 3, 5 — `wstr` объект, `f32` Dist, `u32` Radius, `f32` Angle; 6 — 2 × `wstr` объекта, `u32` Radius |
| предметы | `i32` число; `wstr` имя, `wstr` место, 6 × `u32` (Class, Item.Type, Size, Level, Radius, Owner), `wstr` Useless |
| группы | `i32` число; `wstr` имя, `wstr` планета, `i32` начальное состояние, `u32` Owner, `u32` Group.Type, 7 × `u32` (CntShipMin/Max, SpeedMin/Max, Weapon, CargoHook, EmptySpace), [v<7: `i32`], `u8` AddPlayer, [v<7: 4 × `i32`], 6 × `u32` статусы, `u32` DistSearch, `wstr` Dialog, 2 × `f32` StrengthMin/Max, `wstr` Ruins |
| отношения групп | `i32` число × (`i32` группа 1, `i32` группа 2, `i32` отношение 1→2, `i32` 2→1, `f32` WarWeightMin, `f32` WarWeightMax) — в RSON это связи `TGroupLink` |
| код до состояний | три `wstr` подряд: Init, Turn, DialogBegin (последнего нет при v5) |
| состояния | `i32` число; `wstr` имя, `i32` Move, [Move не 0 и не 5: `wstr` MoveObj], `i32` число целей атаки × `wstr`, `wstr` TakeItem, `u8` TakeAllItem, `wstr` OnTalk, `wstr` OnActCode, `wstr` код эфира, `wstr` Turn-код |
| диалоги | `i32` число × (`wstr` имя, `wstr` код) |
| реплики | `i32` число × (`wstr` имя, `wstr` код: `DText(...)` + Turn-код) |
| ответы | `i32` число × (`wstr` имя, `wstr` код `DAnswer(...)`, `wstr` Turn-код) |

После ответов файл кончается; лишние байты, запись за концом файла, число
записей больше остатка файла — `ParseError` с местом и именем поля.

### Что из этого видно

- Слово по смещению 8 — число глобальных переменных; его же RScript использует,
  чтобы пометить первые `h2` переменных как Global.
- Прежние «две пустые строки перед Init/Turn/DialogBegin» — это нулевое число
  отношений групп (4 нулевых байта). При ненулевом числе старый разбор сдвигал
  подписи слотов: ход становился Init, начало диалога — Turn.
- Приоритет звезды в файле не хранится: звёзды записаны в порядке приоритета,
  а значение переменной звезды — её индекс. Поле «созвездие» −1 даёт
  `Priority` 0; совпадающие приоритеты берутся из этих переменных.
- Версии 7 и 8 читаются одинаково; лишние поля записей — только у версий < 7.
- Версии 5 и 6 читаются, но `parse()` их пропускает (`format version N —
  skipped`): RScript пишет только версию 8, и проверка пересборкой для них
  невозможна.
- `Init` массива в RSON — его длина (RScript создаёт столько пустых элементов)
  или список `[0,5,7]` без пробелов, когда все элементы Int (так у ShuWarriors
  и ArtiDesignDepartment); иначе инициализация элементов теряется.
- Код эфира состояния в RSON не выводится (в корпусах он везде пуст).

## Канон выходного RSON

Выход выровнен по структуре, которую даёт интерактивный SCR-декомпил самого
редактора (и авторские сохранения):

- полная шапка редактора: `FileID … ScriptTextOut`, затем `LangDatIn/LangDatOut`,
  `MainDatIn/Out`, `CacheDatIn/Out`, `ExportLangTxt/ExportLangDat`,
  `Visual.Objects`, `Visual.Links`, `BlockPar.EC.*`. Поля `Export*` намеренно
  `false`, а `LangDatOut` пуст: непустой путь с `ExportLangDat=true` заставил
  бы редактор перезаписать `Lang.dat` мода при компиляции;
- порядок ключей узла: `Type, Name, Pos.x, Pos.y, Parent, #`, затем полезная
  нагрузка (у звёзд — сначала `Constellation`);
- пустой `Attack.Items` не пишется вовсе;
- плашка `Rect.Text` «SCR Decompiling &lt;имя&gt;» с правилами преобразования —
  как её добавляет интерактивный декомпил редактора.

### Раскладка полотна

Воспроизводит структуру, которую даёт интерактивный SCR-декомпил редактора
(**координаты в `.scr` не хранятся** — проверено: в хвосте бинарника код, а не
позиции; редактор раскладывает объекты детерминированным авто-алгоритмом):

- переменные — рядами сверху (шаг 25 по Y, мин. ячейка 60 по X);
- вертикальная колонка слева с шагом 45: корабль → звезда → ряд мест → планета →
  предмет (пустая секция слот не занимает);
- группы — компактной сеткой с переносом (шаг ряда 60, перенос по ширине);
- **каждое состояние — под своей группой** (`+State`-цель группы, `x, y+25`);
  состояния без группы-владельца — рядами ниже сетки;
- Turn-код узла (состояния, диалога, сообщения, ответа) — вплотную слева от
  владельца (`x−20`, тот же `y`);
- диалоги/сообщения/ответы — сетками-рядами (шаг 25);
- служебные опоры Global/Init/Turn/DialogBegin — внизу с шагом 60 по X.

Пиксель-в-пиксель совпадения с редактором нет: ширина ячейки у него зависит от
метрик системного шрифта (проверено — `PlayerState` и
`MachpellaWaitInTortugatzState` получают одинаковую ширину ячейки, а
`NeurolinksNormalState` — 900 px: это расстояния между поддеревьями графа, а не
ширина текста). Наша раскладка приближает структуру, а не точные координаты; на
декомпиляцию и пересборку это не влияет.

## Тексты: Lang.txt / Lang.dat / CT-ссылки

Тексты диалогов хранятся отдельно и адресуются ключами `Script.<Секция>.<N>`.
`Lang.txt` — плоский текстовый формат, парсится напрямую. `Lang.dat` сильно
зашифрован (энтропия ~7.96 бит; XOR/RC4/zlib не подходят) — конвертируется
только `BlockParEditor.exe --cli --convert`.

В сообщениях/ответах диалогов декомпилятор подставляет текст из Lang; в коде
операций CT-ссылки оставлены вербатим — это условие точной пересборки (см.
ниже).

## Round-trip (`--check`) и бинарный патчер

Прямой байт-идентичности при пересборке нет и быть не может:

- RScript **игнорирует dialogs-файл на входе** (только пишет свою таблицу
  ключей) и **ре-ключует все CT-тексты** в своём порядке обработки: дедупит,
  оборачивает строковые литералы в `CT()`/`Format(CT(k),"<0>",0)`, двойные
  обёртки `CT(CT(...))`, отбрасывает переменные в аргументах
  `DText`/`DAnswer`. Оригинальные разреженные ключи невоспроизводимы со
  стороны RSON.

Поэтому после компиляции работает патчер (`run.py`):

1. `_patch_dialog_codes` — выравнивание по вхождениям: найти в оригинале и в
   пересобранном бинаре спаны `CT(...)`/`DText(...)`/`DAnswer(...)` (по ссылке
   `"Script.<имя>."`), спарить их 1:1 по порядку и виду, и вернуть в
   пересобранный файл оригинальные байты спанов. Литералы, обёрнутые RScript'ом
   в CT, восстанавливаются из writeback-таблицы (`newkey=text`), которую RScript
   написал при компиляции. При любом рассинхроне пар — откат без изменений.
2. `_unwrap_literal_formats` — «дожим» по первому дифф-байту, циклом: развернуть
   `Format(<лит>,"<0>",0,...)` обёртки, выровнять нулевой паддинг и пробельные
   сдвиги (реиндентация кода), вернуть съеденные экранирования `\'`, восстановить
   отрицательные значения, зажатые в `-1`, цифры плейсхолдеров `<N>`,
   1-ulp дрейф float-полей и структурные вставки/удаления старых версий записей
   (со строгой ресинхронизацией по 24 байтам).
3. Финальный арбитр — побайтовое сравнение. **Ложный MATCH возможен**: шаг 2
   вставляет и удаляет нули и пробелы по оригиналу, поэтому не видит, например,
   код, перенесённый между пустыми слотами Init/Turn/DialogBegin, или поля
   записи, сдвинутые на нулевые байты. Так проходил AdvancedArts версии 7 при
   неверно прочитанной группе и коде начала диалога, подписанном как Init
   (выяснено 12.10.2026 сборкой RScript без доводки и сравнением полей через
   `read_scr_layout`).

Ограничение патчера: он реконсилирует **подстановки**, а не **вставки** —
для вставок кода нужно редактировать UTF-16-исходник в бинаре напрямую
(nt-формат это позволяет: строки null-terminated).

Замечания:

- RScript падает «Runtime error 217» на выходе (безвредно) и показывает
  модальные окна с реальными ошибками — `_dlgwatch.py` находит окна процесса
  (Win32 `#32770`), жмёт OK и возвращает текст в лог; пустой Global-слот
  эмитится как `['//']`, иначе RScript падает.
- Оставшийся класс расхождений — version-diff: старый компилятор иначе
  нумерует `Format`-плейсхолдеры `<N>` (ренумерация `<1>`→`<0>` и т.п.),
  такие файлы дают стабильный MISMATCH при полной корректности контента
  (на модах Steam 12.10.2026 — ExpTC, DrKles_Blazer, SR1Gaals&Pirates; по полям
  все три собираются в исходную структуру). RevDominatorSpy, ShuMiniBoss и
  ArtiDesignDepartment, которые прежде относили сюда же, на деле теряли связи
  звёзд, отношения групп и инициализацию массивов — с 12.10.2026 это MATCH.

## Стрелки диалогов остаются кодом

Важный факт, подтверждённый эталоном (интерактивный SCR-декомпил редактора,
`*_recovery.rson`): переходы `DChange(N)` / `DAdd(N)` / `ChangeState(x)` внутри
операций **остаются в коде вербатим**, редактор их в стрелки НЕ превращает. Он
рисует только «структурные» связи (`Visual.Links`): объект→объект
(корабль→звезда, планета→звезда, группа→планета, группа→состояние, место→звезда,
предмет→место, звезда→звезда `TStarLink` с условием расстояния, группа→группа
`TGroupLink` с отношениями) и диалоговый узел→его Turn-код. Ровно этот набор связей строит и
наш декомпилятор — то есть «стрелки» уже присутствуют в обычном `.rson`, и
отдельная «графовая» форма не нужна.

## Валидация

- `run.py --check` — побайтовый MATCH после патчера; из-за «дожима» он может
  пропустить расхождение (см. выше).
- Строже — собрать RSON RScript'ом без патчера и сравнить `read_scr_layout`
  оригинала и сборки по полям; в коде — ключи `CT(...)` и строковые литералы
  заменить меткой, пробелы и комментарии убрать, `DText(...)`/`DAnswer(...)`
  вырезать (их RScript строит из текстов). Так проверено исправление чтения
  12.10.2026.
- `validate.py` — быстрая сверка счётчиков групп/состояний/диалогов с
  эталонными `.rson` из `rsons/` (авторские файлы редактора — золотой источник
  схемы полей).
- Полезный приём при отладке: у авторских раздач рядом с `.scr` бывают
  `_dump.txt` — вербатим-дампы бинарника (UTF-16), удобны для построчного
  диффа кода.

## Формат PKG (архивы ресурсов)

Реализован в `srpkg.py`. Формат реверснут на реальных файлах игры и сверен с
эталонным загрузчиком OpenSR (`Ranger/PKG.cpp`, `Ranger/ZLib.cpp`,
`include/OpenSR/libRanger.h`). Всё little-endian.

```
file[0]            u32  offset заголовка корневой директории (всегда 4)

dir header (12 B)  u32 zero1 = 170   (константа: 12 + 158)
                   u32 itemsCount
                   u32 zero2 = 158   (константа: размер записи)
                   далее itemsCount записей по 158 байт

item (158 B)       u32 sizeInArc     размер данных в архиве (с 4-байт префиксом)
                   u32 size          распакованный размер
                   char[63] fullName имя в ВЕРХНЕМ регистре (для поиска)
                   char[63] name     имя как есть
                   u32 dataType      1=RAW, 2=ZL02(zlib), 3=директория
                   u32 dataType      дубль того же значения (@+138)
                   u32 0, u32 0
                   u32 offset        для dir — смещение её dir header;
                                     для файла — смещение блока данных
                   u32 0

блок данных        u32 prefix = sizeInArc - 4    (= длина payload ниже)
                   payload:
                     RAW  (type 1): `size` байт как есть
                     ZL02 (type 2): цепочка чанков, ≤64 KiB распакованных на чанк:
                                    [u32 packed]["ZL02" u32 rawSize zlib-данные]
                                    где packed = 8 + len(zlib)
```

Раскладка — depth-first: заголовок директории, её таблица записей, затем для
каждого потомка сразу его блок (вложенная директория целиком или данные файла).
Корневой заголовок лежит по смещению 4, первые 4 байта файла — указатель на него.

ZL02/ZL01 — тонкая обёртка над стандартным zlib (`compress`/`uncompress`):
сигнатура + u32 распакованного размера + zlib-поток, level 9, чанки по 64 KiB.

**Байт-в-байт перепаковка.** `srpkg pack` пересобирает любой стоковый архив
побайтово идентично оригиналу — проверено на всех 19 файлах `DATA/` (9087
файлов). Правило выбора RAW/ZL02 и раскладку записей ResEditor восстановлены
диффингом оригиналов:

- **RAW или ZL02 — по имени и размеру, НЕ по фактической сжимаемости.** Файл
  хранится RAW тогда и только тогда, когда это `.jpg`/`.png` (уже сжатые
  форматы) или его размер меньше 128 байт; всё остальное — ZL02. Часть файлов
  ≥128 Б пишется в ZL02, даже если zlib их раздувает, — проверка «а сжалось ли»
  дала бы неверный тип и сломала бы перепаковку.
- **Порядок записей в директории:** сначала все поддиректории, затем все файлы;
  внутри каждой группы — регистронезависимая сортировка имён (по верхнему
  регистру), а не по ASCII-кодам (иначе строчные уезжают после прописных).
- **Поле `fullName`** переводит в верхний регистр и кириллицу cp1251 (`а-я`
  0xE0–0xFF → `А-Я`, `ё`→`Ё`), а не только латиницу — существенно для модов с
  русскими именами файлов.

`srpkg verify` — round-trip самотест по содержимому; для строгой байтовой сверки
достаточно `pack` распакованного каталога и сравнения с оригиналом.

**Батч по каталогу.** `list`/`unpack`/`verify` принимают каталог и рекурсивно
обходят все `*.pkg`. `unpack <dir> <out>` кладёт каждый архив в `out/<путь>.pkg/`
(«пакет-директория» — расширение сохраняется в имени папки), а `pack <dir> <out>`
с выходным аргументом без `.pkg` собирает все такие `*.pkg/`-каталоги обратно —
точный round-trip `unpack ↔ pack`. Направление `pack` задаётся выходом: путь на
`.pkg` → один архив, каталог → батч.

## Формат изображений gi/gai/hai (декодер -> PNG)

Реализован в `srgi.py` (`python run.py gi info|decode|verify`). Форматы реверснуты
на реальных файлах игры и сверены с эталонными загрузчиками OpenSR
(`Ranger/GILoader.cpp`, `GAILoader.cpp`, `HAILoader.cpp`,
`include/OpenSR/libRangerQt.h`). Всё little-endian. Только stdlib + zlib —
**без Pillow** (PNG пишется своим мини-энкодером: `IHDR` + `zlib(IDAT)` + CRC32
из `binascii`). Цвет нормализуется в прямой (не premultiplied) RGBA8888.

Реализованы **и декодер** (gi/gai/hai -> png), **и энкодер** (png -> gi/gai/hai);
запаковка результата обратно в архив — `srpkg pack`. Спека энкодера — в конце раздела.

### GI — одиночный кадр (сигнатура `0x00006967` "gi")

```
GIFrameHeader (64 B)  u32 signature, version, startX, startY, finishX, finishY,
                      rBitmask, gBitmask, bBitmask, aBitmask, type, layerCount,
                      unknown1..4
GILayerHeader (32 B)  u32 seek, size, startX, startY, finishX, finishY, unk1, unk2
                        seek  — смещение данных слоя ОТ начала кадра
                        size  — длина данных слоя в байтах (гейт расхода, см. ниже)
RLE-преамбула (16 B)  i32 rleSize, u32 w, u32 h, ... , палитра-размер в байте @+12
                        (0 -> 256); дальше палитра и/или RLE-поток
```

Канвас кадра = `(finishX-startX) x (finishY-startY)`; координаты слоёв
нормализуются к началу кадра (для GAI — к рамке анимации, чтобы все кадры делили
одно полотно). Шесть типов кодирования (`GIFrameHeader.type`):

| type | слои | кодирование |
|---|---|---|
| 0 | 1 | сырые сканлайны: 16-бит R5G6B5 (`w*h*2`) или 32-бит ARGB по маскам (`w*h*4`, порядок B,G,R,A) |
| 1 | 1 | RLE 16-бит R5G6B5, непрозрачный |
| 2 | 3 | тело (R5G6B5 RLE) + обводка (R5G6B5 RLE) + альфа (6-бит RLE, только альфа-канал) |
| 3 | 2 | индексы в палитру R5G6B5 (RLE) + индексы в палитру цвет+альфа (RLE) |
| 4 | 2 | сырые 8-бит индексы + RGBA-палитра (`size/4` записей, порядок r,g,b,a) |
| 5 | 1 | delta-кадр GAI: аддитивное наложение на предыдущий кадр |
| 6 | 1 | битовый delta-кадр GAI (HD-анимации), см. ниже |

RLE-опкод: `0`/`0x80` — новая строка; `>0x80` — литерал `(b&0x7f)` пикселей;
`<0x80` — пропуск `b` пикселей вправо. Расширение R5G6B5→8-бит — top-justified,
как в OpenSR: `R=(c>>11&0x1f)<<3, G=(c>>5&0x3f)<<2, B=(c&0x1f)<<3`. 6-бит альфа:
`a8 = 4*(63-a6)`.

Преамбула RLE-слоя (типы 1/2/3) во всём стоке устроена одинаково — проверено на
всех 10656 слоях type-1, 55494 type-2 и 5820 type-3:

```
i32@+0  длина RLE-потока (БЕЗ преамбулы и палитры)
u32@+4  ширина СЛОЯ (не кадра), u32@+8 — высота слоя
 u8@+12 размер палитры (0 -> 256); только у палитровых слоёв type-3, иначе 0
```

⇒ `GILayerHeader.size == 16 + байты палитры + длина RLE-потока` — 0 исключений.
Newline-опкодов ровно по одному на строку слоя, включая последнюю (обе записи,
`0x00` и `0x80`, встречаются; `0x00` доминирует). Боксы слоёв **кропаются под
нарисованное** и независимы друг от друга: у `DATA/Weapon/Bomb.gai` слой 0 —
бокс 1×1 внутри кадра 25×22.

Delta-кадр (type 5): 16-байт преамбула задаёт 4 сдвига `shlc` (по каналам B,G,R,A)
и `skip = u32@+8 << 2`; дальше поток аддитивных дельт по каналам с терминатором
`0x40` (см. `decode_delta`, порт `decodeGAIDeltaFrame`). Каналы OpenSR идут в
порядке памяти B,G,R,A — маппятся на байты RGBA через `_DELTA_CH = (2,1,0,3)`.

Поля преамбулы type-5 разобраны на всех 6133 стоковых кадрах, 0 исключений:

```
u32@+0  длина потока опкодов, u32@+4 — ширина слоя
u32@+8  число ПРОПУСКАЕМЫХ dword'ов == высота слоя: это таблица смещений строк,
        по u32 на строку, монотонная, отсчёт ОТ начала слоя (первая == 16+4*h)
 u8@+12/+13  нибблы shlc: 0x88,0x88 -> сдвиги 0 (полные 8 бит, 4073 кадра),
        0x65,0x55 -> 5,6,5,5 (2060 кадров); маски заголовка совпадают с выбором
```

OpenSR эту таблицу просто перепрыгивает (`dev->seek(pos + offset)`), но пишут её
все стоковые кадры, поэтому энкодер её генерирует. Поток дельт заканчивается
ровно на границе слоя (проверено на выборке 400 кадров) — `gi verify` требует
точного расхода, как и для остальных типов.

### Delta-кадр type 6 — битовый (HD-анимации; в OpenSR ЕГО НЕТ)

Реверснут из `okgf.dll!OKGR_F6_DrawRGBA` (экспорты `OKGR_F5_DrawRGBA`/`F6_DrawRGBA`
= декодеры кадров типа 5 и 6; игра дёргает их через тонкие Delphi-обёртки
`0x4bdcc2`/`0x4bdd4c`). Заголовок потока — 4 байта:

```
byte0  младший ниббл -> ширина канала 0, старший -> канала 1   (хранится как 8-n)
byte1  то же для каналов 2 и 3      (0x65,0x55 => 5,6,5,5 бит = R5G6B5A5)
u16@2  число блоков
далее  битовый поток
```

Биты берутся из байта **младшими вперёд**, но поле собирается **старшими вперёд**
(первый прочитанный бит — старший в значении); см. `srgi._Bits` — точный порт
битридера из DLL. Грамматика:

```
блок:      x:10, y:10            — курсор на (x,y) от начала КАДРА (frame box)
  сегмент: width:3, chan:2
     width==0 && chan==0  -> курсор на строку ниже
     width==0 && chan==1  -> конец блока
     width==0 && chan>=2  -> прогон команд: 1 -> обнулить пиксель (4 байта в 0),
                             0 + n:3 -> пропустить n пикселей (n==0 — конец)
     width>0              -> sign:1, затем по пикселю: 1 -> v:width, дельта
                             (v+1)<<shift[chan] прибавляется (sign=0) или
                             вычитается (sign=1) по модулю 256; 0 + n:3 —
                             пропуск n пикселей (n==0 — конец сегмента)
```

Каналы — тот же порядок памяти B,G,R,A, что и в type 5 (`_DELTA_CH`), и кадры
так же **кумулятивны** (накладываются на предыдущий). Обе детали проверены
эмуляцией: `OKGR_F6_DrawRGBA` прогнан под unicorn на реальных кадрах, вывод
Python-декодера совпал с ним **байт-в-байт** (`HumanGov0` — рамка кадра равна
рамке анимации, `GaalMC0` — кадры смещены `(150,45)`, проверено и это). Инвариант
расхода строгий: битовый поток кончается **ровно** на границе `GILayerHeader.size`
(проверяется в `gi verify`). В корпусе игры type 6 встречается только в HD-ветке
правительства: 13 из 20 анимаций `DATA/Govhd/` (1339 кадров), остальные 7 — type 5.

### GAI — анимация (сигнатура `0x00696167` "gai")

```
GAIHeader (48 B)  u32 signature, version, startX, startY, finishX, finishY,
                  frameCount, haveBackground, waitSeek, waitSize, unk1, unk2
затем             frameCount x (u32 giSeek, u32 giSize)   таблица кадров
затем             блок таймингов по (waitSeek, waitSize)
```

Каждый кадр — полный GI-кадр по своему `giSeek` (может быть обёрнут ZL01/ZL02 —
одиночный `unpackZL`, не чанкованный как в pkg). Кадры декодируются
последовательно: keyframe (type 0..4) полностью замещает полотно, delta-кадр
(type 5) накладывается на предыдущий. Тайминги (`load_gai_times`, порт
`loadGAITimes`): блок `u32 timeBlockCount`, затем по блокам пары `(frame, time_ms)`.
На выходе `decode` — `<stem>_NNN.png` + `<stem>.times.json`.

**`haveBackground=1` — ключевой кадр лежит СНАРУЖИ, в соседнем `<stem>.gi`.** У
таких анимаций кадр 0 в самом gai пустой (`giSeek=giSize=0`) либо сразу delta, и
без внешнего кадра дельты накладываются на прозрачный холст — получается контур
вместо картинки (так выглядели анимации правительства `DATA/Gov/*`). `decode`
подхватывает соседний `.gi` автоматически (`find_background`, регистронезависимо —
в игре есть и `2PeopleAnim0.gi`, и `2Gaal2Anim0.GI`), декодирует его **в
координатах рамки анимации** (`decode_background`) и кладёт имя в
`<stem>.times.json` (`"background"`). Переопределяется `--bg FILE.GI`, отключается
`--no-bg`. По стоковому корпусу: 182 gai с `haveBackground=1`, у 180 сосед на
месте, 2 без него (`SI/2_1c.gai`, `FormLoad2/2Elemental.gai` — предупреждение в
stderr, декодируются как раньше). Если первый кадр анимации полный (type 0..4),
фон ни на что не влияет — проверено покадрово на `Captain/2Fei0`.

Побочно: фоновый `.gi` часто **больше** рамки анимации (`FormShip2/2CenterNormal`
— 334×249 против рамки `(24,17)-(307,232)`), а примитивы отбрасывали ран/строку
целиком, если она частично вне полотна, — фон декодировался пустым. Теперь ран
клипается (`_clip_run`) в `blit_r5g6b5`, `draw_r5g6b5`, `draw_rgbi`, `draw_ai`,
`decode_indexed`; расход байт (инвариант `GILayerHeader.size`) не меняется.

### HAI — мультиразрешение (сигнатура `0x04210420`, HUD 128/256/384)

```
HAIHeader (52 B)  u32 signature, width, height, rowBytes, count, frameSize,
                  unk1..6, palSize
затем             count x (height*rowBytes 8-бит индексов + palSize палитра RGBA)
```

Кадр `i` лежит по `52 + i*(height*rowBytes + palSize)`: `height*rowBytes` индексов
(строка = `rowBytes` байт, из них значимы первые `width`) + палитра `palSize` байт
(`palSize/4` записей RGBA, порядок r,g,b,a). Время кадра — константа 50 мс.
Инварианты: `frameSize == height*rowBytes + palSize`, `52 + count*frameSize <=
размер файла`. Строгого равенства нет: у части **корабельных** HAI после основного
блока из `count` кадров дописаны копии анимации в более высоком разрешении (это и
есть «мультиразрешение»); заголовок описывает основной блок, `decode_hai` читает
ровно `count` кадров, хвост игнорируется. Проверено: `DreadnoughtFei.hai` — 200
кадров 256×256 декодируются в чистый спрайт, за ними ~16 МБ до-записанного хвоста.

### Гейт качества (`gi verify`)

Энкодера пока нет, поэтому вместо байт-в-байт round-trip (как у pkg) — самотест на
самосогласованность, но с байт-точными проверками там, где они достижимы:

- **Ре-сериализация заголовка байт-в-байт**: распарсенные `GIFrameHeader` +
  все `GILayerHeader` пакуются обратно и сравниваются с оригиналом (доказывает
  lossless-разбор структуры, включая `unknown`-поля).
- **Инвариант расхода**: RLE/сырьё-декодер каждого слоя обязан съесть **ровно**
  `GILayerHeader.size` байт (`16 + rleSize` для RLE, `16 + палитра + rleSize` для
  индексных, `w*h*bpp` для сырых). Проверено сходится на всех типах.
- **Размер канваса** совпадает с рамкой кадра; delta-поток (type 5/6) тоже
  заканчивается ровно на границе слоя.
- **GAI/HAI**: все кадры декодируются без исключений; для HAI — размерные
  инварианты выше.
- **Глазная сверка** нескольких PNG против ResEditor 1.3.2 (GUI-эталон) — вручную.

### Энкодер (png -> gi/gai/hai)

`gi encode` — инверсия декодера. Свой мини-**PNG-ридер** (stdlib+zlib, без Pillow):
IHDR/PLTE/tRNS/IDAT, non-interlaced, цветовые типы 0/2/3/4/6 при 8 бит, палитра/grey
при 1/2/4 бит, любой тип при 16 бит (берётся старший байт), все пять фильтров скан-строк
(None/Sub/Up/Average/Paeth) — на выходе прямой RGBA8888. Каждый `encode` **самопроверяется**:
декодирует собственный вывод и сравнивает пиксели.

**Гейт качества для lossy-форматов.** Родные RLE-типы теряют по построению (цвет →
R5G6B5, альфа → 6 бит), поэтому `decode(encode(png)) == png` для них невозможен.
Критерий вместо него: энкодер обязан **только квантовать** — `decode(encode(x))`
совпадает с `quantise_gi(x, fmt)`, эталоном того, что формат вообще способен
выразить. Так проверяются все типы, включая `rgb565` (раньше он просто
пропускался). Плюс инвариант расхода слоя (`gi verify`) на каждом кадре.

- **GI по умолчанию — type-0 straight-ARGB** (`_gi_header` + BGRA-сканлайны): рамка
  `(0,0)-(w,h)`, один слой `seek=96, size=w*h*4`, маски `A=ff000000 R=ff0000 G=ff00 B=ff`,
  `version=1`, `unknown=0` — байт-в-байт как стоковые `2Ship*.gi` (в корпусе 31 такой файл),
  поэтому lossless: `decode(encode(png)) == png`. `--format rgb565` — type-0 R5G6B5
  (непрозрачный, `size=w*h*2`, потеря цвета). `--format indexed` — type-4: два слоя
  (`seek0=128` сырые индексы `w*h` + палитра `npal*4` RGBA), lossless при ≤256 цветах,
  иначе явная ошибка.
- **Родные RLE-типы** (`--format rle565` / `rle-alpha` / `rle-indexed` = типы 1/2/3):
  общий писатель `_rle_layer` (литерал `0x80|cnt`, пропуск `cnt<0x80`, newline `0x00`
  ровно раз на строку) + `_crop_cells`, кропающий бокс слоя под нарисованное.
  - **type-1** — один слой, непрозрачный; сохранить можно только полную прозрачность
    (пропуском), всё остальное становится alpha 255.
  - **type-2** — весь цвет в слой 0, обводка (слой 1) **пустая** (так в 512 стоковых
    кадрах). Тонкость: 6-бит альфа упирается в `4*(63-0) = 252`, непрозрачный пиксель
    в ней невыразим — и не нужен, слой 0 уже кладёт alpha 255, а пропуск в альфа-слое
    её сохраняет. Поэтому **слой 2 хранит только полупрозрачную кайму**: и точнее
    (255 остаётся 255), и заметно меньше.
  - **type-3** — та же логика разводки по палитрам: непрозрачные пиксели идут в слой 0
    (палитра R5G6B5), полупрозрачные — в слой 1 (палитра цвет+альфа); ≤256 записей
    на палитру, иначе явная ошибка.
- **GAI — все кадры keyframe** в выбранном формате, либо **`--format delta`**:
  кадр 0 — lossless ARGB-keyframe, дальше type-5 дельты к предыдущему кадру. Сдвиги
  `shlc` нулевые (`0x88,0x88`), поэтому дельты несут все 8 бит и **вся анимация
  остаётся lossless** — гейт тут строгий, байт-в-байт. Хранится только изменившийся
  бокс; пробеги упаковываются жадно с выбором из четырёх ширин опкода (1/2/4/8 бит)
  по стоимости на пиксель. Совпавший с предыдущим кадр вырождается в слой нулевого
  размера. Раскладка файла: `GAIHeader` (рамка `0,0..W,H`, `haveBackground=0`),
  таблица `frameCount×(seek,size)`, затем **блок таймингов** байт-в-байт как у игры
  (одиночный блок: `u32 1`, пара seek `(12,14)`, 2-байт зазор, `u32 frameCount`, далее
  `frameCount×(u32 кадр, u32 мс)`; размер `18+8·n`), затем кадры — порядок обхода
  загрузчика игры.
- **HAI** — как каждый стоковый: `rowBytes==width`, `palSize==1024` (256 RGBA-записей,
  неиспользуемые нулём), `frameSize=height*rowBytes+palSize`, `unknown=(1,8,0,0,0,0)`;
  на кадр — свои `h*width` индексов + палитра. Требует ≤256 цветов на кадр (у
  декодированного HAI всегда так).

- **Батч дерева** — инверсия `decode <dir>`. При каталожном выходе `encode` обходит
  дерево и собирает обратно: каждая группа `<stem>_NNN.png` → `.gai`/`.hai`, каждый
  одиночный `*.png` → `.gi`, структура зеркалируется. Однозначность gai-vs-hai даёт
  поле **`kind`**, которое `decode` пишет в `<stem>.times.json` (легаси-сайдкары без
  него трактуются как gai). Группировка: `.times.json` перечисляет свои кадры
  (`<stem>_NNN.png`) — они «съедаются», всё оставшееся `*.png` = одиночные gi.

Проверка энкодера — round-trip по корпусу игры: `decode(x) -> rgba -> encode -> decode`,
сравнение RGBA-буферов (для argb/indexed/delta/gai/hai — точное совпадение, для RLE-типов
— с `quantise_gi`). Батч дерева проверен сквозным
`decode <tree> dec/ && encode dec/ reb/ && decode reb/ dec2/` — все PNG и `kind` в
`dec2/` совпадают с `dec/`.

**Что даёт родной тип по размеру** (мод `DenUIRecolor`, 1778 файлов `.gi`, все
исходно type-2; размер в архиве считается через `srpkg._encode_payload`, т.е. ровно
как ляжет в `.pkg`):

| чем пересобрано | в архиве | к оригиналу |
|---|---|---|
| нативный type-2 (как собрал автор мода) | 28 631 851 Б | 1.000× |
| `argb` (type-0, прежний дефолт) | 34 523 617 Б | **1.206×** |
| `rle-alpha` (type-2, наш энкодер) | 27 918 694 Б | **0.975×** |

То есть полный реген графического мода через type-0 стоил +20,6 % в архиве
(zlib этого не съедает), а родной type-2 не только закрывает разрыв, но и выходит
на 2,5 % компактнее авторских файлов. Гейт прошли все 1778 файлов, 0 расхождений.

Для анимаций (9 `.gai` того же мода, тоже размер в архиве) картина иная — там
выигрывают дельты, а не RLE:

| чем пересобрано | в архиве | к оригиналу |
|---|---|---|
| оригинал автора | 10 954 382 Б | 1.000× |
| `argb` keyframes | 9 219 167 Б | 0.842× |
| `rle-alpha` keyframes | 11 063 354 Б | 1.010× |
| **`delta`** (lossless) | **8 298 712 Б** | **0.758×** |

RLE-кадры хуже сырых ARGB именно в архиве: RLE-поток уже «сжат» и zlib берёт с
него меньше. Дельты выигрывают у всех и при этом ничего не теряют.

**Пер-кадровая ZL-обёртка не нужна.** Кадры GAI бывают завёрнуты в одиночный
ZL01/ZL02 (декодер это понимает), но в стоке так сделаны единицы (в выборке 300
анимаций — 16069 сырых кадров против 90 обёрнутых), а главное — внутри `.pkg`
разницы нет: у пары замеренных файлов обёртка дала 233 506 против 222 049 Б и
6 370 239 против 6 483 639 Б, т.е. ±2 % в обе стороны. Архивный ZL02 эту работу
уже делает, поэтому энкодер пишет кадры сырыми — как и сама игра.

## Известные ограничения

- Формат `h0=6` (очень старые скрипты) не поддержан — файлы пропускаются.
- Небольшой класс файлов даёт `check=MISMATCH` из-за version-diff компилятора
  (см. выше) — содержимое декомпиляции при этом корректно.
- `--check` и авто-закрытие окон работают только на Windows (RScript — win32).
- Парсер ограничен таймаутом на файл (`PARSE_TIMEOUT`, 10 c) — зависшие
  разборы пропускаются с пометкой TIMEOUT.
